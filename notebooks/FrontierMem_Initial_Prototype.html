FrontierMem: Initial Counterfactual Prototype¶

Learning when a user preference should be applied, ignored, or clarified¶

This notebook is an advisor-ready, fully reproducible proof-of-concept for the core FrontierMem idea:

A personalized assistant should not store only what the user prefers; it should also model where that preference is valid.

The prototype intentionally uses an interpretable offline extractor so that every stage can be inspected. It validates the formulation, data construction, metrics, and end-to-end decision pipeline before replacing the extractor with a trained open-source LLM.

1. Experimental design¶

We build counterfactual twin histories. The twins contain the same surface request, but the reason behind the request differs:

  • Stable preference: the behavior is broadly representative of the user.
  • Scoped preference / temporary constraint / other owner: the behavior is valid only in a specific context.

The same current request is then evaluated against both histories. A model must choose one of:

  • APPLY — use the preference;
  • IGNORE — the request is outside the applicability boundary;
  • CLARIFY — the request is near an uncertain boundary.

The evaluation includes writing, education, travel, and food scenarios.

3. A counterfactual twin example¶

Both histories contain the same surface sentence, but one reflects a stable preference and the other a temporary reimbursement constraint. The boundary-crossing query should therefore receive different decisions.

family = 'travel_budget'
group_id = df.loc[df['family'].eq(family), 'group_id'].iloc[0]
example = df[(df['group_id'] == group_id) & (df['query_kind'] == 'crossing')].sort_values('profile_variant')

Preliminary observation¶

  • The flat fact-memory baseline overgeneralizes on every outside-boundary case.
  • A direct long-context classifier learns many surface cues but loses performance under held-out paraphrases.
  • FrontierMem-Lite reaches strong accuracy while preserving an explicit, inspectable memory representation.
  • The result is not presented as a final SOTA claim; it demonstrates that the problem and metrics are operational and that a boundary-aware architecture can be implemented end to end.

7. What is already implemented¶

  • Controlled counterfactual twin generation
  • Stable preference vs. state, constraint, context-dependent preference, and other-owner cases
  • Structured memory with scope, temporal validity, ownership, evidence, and confidence
  • Boundary-aware APPLY / IGNORE / CLARIFY policy
  • Flat-memory, query-only, and raw-history baselines
  • Group-disjoint and lexical-holdout evaluation
  • Overgeneralization and counterfactual twin metrics
  • Reproducible tests and CLI inspection

8. Next implementation stage¶

  1. Replace the rule-based extractor with a Qwen/Llama 3B--8B structured-output model.
  2. Create SFT targets using the same memory schema.
  3. Add counterfactual contrastive training for twin histories.
  4. Generate natural open-ended responses conditioned on the chosen action.
  5. Evaluate on PersonaMem-v2 subsets and a human-validated FrontierSuite.

9. Honest interpretation for the meeting¶

This prototype is evidence that the project is well-defined and executable. The current numerical results come from a controlled synthetic suite and an interpretable lightweight method. They should be presented as preliminary validation of the research hypothesis and experimental pipeline, not as final evidence that the full LLM personalization problem is solved.
